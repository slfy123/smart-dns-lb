# Smart DNS LB 第一版设计

日期：2026-10-26

## 1. 目标与确认的环境

用户有三台或更多线路机和一台落地机，服务端使用 3x-ui / VLESS，客户端使用 Clash 系列客户端。用户已确认传输范围为 TLS + TCP、WebSocket 或 gRPC。

交付一个可部署在 Ubuntu / Debian 落地机上的项目：Python 控制服务、权威 DNS、中文 Web 面板、真实链路探测和安装脚本。客户端使用一个固定入口域名；系统根据路径状态为新的 DNS 查询选择入口 IP。

支持两种现有转发布局：线路机以 Realm / Gost 透明转发至落地机，或线路机先终止 VLESS 再由既有 Xray 路由转发至落地机。本项目管理 DNS 和探测，不自动改写现有 3x-ui / Realm / Gost 配置。

## 2. 第一版范围和约束

- Python 3.10+；DNS、API、状态判定与调度运行在同一 Python 进程、单一 asyncio 事件循环中。
- 使用 dnslib 编解码 DNS；FastAPI / Uvicorn 提供 API；SQLite 保存配置和关键事件。
- 为验证真实 VLESS 连接，允许一个受管理的 Mihomo 辅助进程。这是相对于“所有功能严格单进程”草案的明确调整。控制服务保持单进程，辅助进程仅负责协议执行。
- 前端为本地 HTML / CSS / JavaScript，深色中文界面，无 Node.js 编译要求、无运行时 CDN 依赖。浏览器每两秒刷新状态。
- 第一版实现 IPv4 线路 A 记录调度、IPv4/IPv6 客户端 DNS 查询的正确响应、单管理账户与审计事件。线路 AAAA 调度、集群同步、自动证书申请、DNSSEC、流量遥测暂不包含。
- 管理 API 默认绑定 127.0.0.1:8080；DNS 默认绑定配置指定的服务地址 UDP/TCP 53。公开管理入口通过 HTTPS 反向代理或管理隧道访问。
- Uvicorn 固定单 worker，生产服务关闭 reload。

## 3. 组件与目录

- `app.py`：启动入口、生命周期、Uvicorn 集成。
- `smart_dns/config.py`：Pydantic 校验、配置版本、SQLite 持久化与迁移。
- `smart_dns/state.py`：运行状态、不可变 DNS 调度快照、统计。
- `smart_dns/dns.py`：UDP/TCP 权威响应，区域边界和协议错误处理。
- `smart_dns/prober.py`：并发探测、健康状态机、辅助进程管理。
- `smart_dns/scheduler.py`：四种调度模式、时间窗口和全故障策略。
- `smart_dns/api.py`：鉴权、配置 CRUD、实时状态、事件。
- `templates/index.html` 和 `static/`：面板及本地静态资源。
- `install.sh`、`requirements.txt`、`README.md`、示例配置、测试和 systemd 服务模板。

拆分模块是为了避免将 DNS 协议、进程管理和网页 API 混在一个大文件中；用户运行入口仍为 app.py。

## 4. 配置模型

全局配置包含：区域名称、服务名称、权威 NS 名称与地址、SOA 参数、TTL、监听地址、探测周期/超时/并发、失败与恢复阈值、恢复观察期、探测有效期、调度模式、全故障策略、峰值时段、时区、测试地址及出口验证。

域名规范化为绝对域名并校验服务名称位于区域内。区域 apex 固定配置 SOA / NS。新增服务名称、修改区域或 NS 后提示重新核对父区委派。

节点包含：稳定 UUID、名称、入口 IPv4、端口、NORMAL/PREMIUM、启用状态、权重、优先级、最大延迟、VLESS 连接参数、最近探测版本。VLESS 参数覆盖 UUID、TLS SNI、证书验证、TCP / WS / gRPC、WS path/Host、gRPC service-name 和与实际客户端一致的其他受支持字段。

支持导入单个 Mihomo VLESS 节点的 YAML/JSON 片段。只接受白名单字段；拒绝整份任意 Mihomo 配置、外部 provider、脚本和任意控制端口。节点 server 被固定为其入口 IP，TLS SNI 和 WS Host 等保持显式配置值。默认开启证书校验；兼容自签名环境的选项须显式启用并在面板展示。

权重范围为 0..10000，优先级为正整数；零权重节点不参与加权模式，但仍可探测。配置验证拒绝让某个已配置的加权策略候选类别全部零权重。延迟、超时、并发、TTL 和时间窗口均有范围约束。

## 5. 探测和协议执行

每轮对启用节点进行有并发上限的端到端检查；周期按单调时钟调度并错峰，同一节点只运行一个探测任务。快速故障发现优先于高频采集大量指标。

Mihomo 通过受控生成的配置提供每个节点独立的本地 SOCKS 入口；每个入口固定路由到对应 VLESS 节点，禁止 DIRECT 或其他节点回退。辅助进程的控制接口仅在本机开放并使用随机密钥；配置和密钥文件权限为 0600。

探测器经该节点专用 SOCKS 入口请求配置的 HTTPS 测试地址。测试地址支持配置预期状态码、预期文本或 JSON 字段，以及预期出口 IP。请求禁用环境代理、限制重定向、限制响应体大小，使用缓存规避参数；所有阶段共享总超时预算。

健康标准分为：

1. 传输与认证可用：经指定 VLESS 节点取得验证通过的 HTTPS 响应。
2. 路径已核实：在上项基础上，响应的出口标识匹配配置的预期落地出口。

未配置出口身份校验时，面板明确展示“业务请求成功，出口未核实”；完整路径验收必须启用出口校验。所有样例测试地址仅是可替换示例；程序不会将示例地址的偶发故障当成已证实的三线路故障。

入口 TCP 检查作为故障诊断信息，不单独使节点成为健康。请求耗时命名为“端到端探测耗时”，与 TCP 建连耗时分别记录，不标称为用户网络延迟。

辅助进程不存在、崩溃或配置错误时，状态为“探测不可用”；系统不会仅根据入口 TCP 成功发布健康线路。进程崩溃采用有限频率的退避重启，事件记录不包含凭证。新增/修改节点先验证生成配置，再切换辅助进程和节点配置版本，旧版本探测结果不得覆盖新状态。

默认使用两个独立 HTTPS 检查目标：主目标失败时尝试备目标；只有本轮目标均失败且控制组访问成功时才计入该节点失败。控制组是探测主机直接访问同组目标的独立检查，仅用于区分探测目标故障；它不作为节点健康证据。若所有目标及控制组均失败，则标记本轮观测不确定，不递增线路故障计数。出口身份校验可配置于每个目标；只有完成身份校验的成功请求才满足“路径已核实”。

落地机内的探测覆盖回路及代理出口，不代表用户网络到入口的质量；保留外部探测器接口的数据模型，但第一版不部署外部探测代理。

## 6. 状态机与观测异常

节点状态为 UNKNOWN、UP、DEGRADED、DOWN、RECOVERING、DISABLED、STALE。UNKNOWN 和 RECOVERING 默认不发布。手动禁用优先级最高，并持久保存。

默认每 5 秒探测，总超时 3 秒，连续失败 3 次进入 DOWN，连续成功 3 次后进入恢复观察，稳定 30 秒才进入 UP。恢复期间出现失败回到 DOWN。首次启动节点在连续成功达到恢复阈值后可进入 UP，无须额外故障恢复观察期。

延迟按 EWMA 平滑。超过 max_rtt 的连续成功请求进入 DEGRADED，连续恢复到阈值以下的 80% 才恢复 UP。DEGRADED 在健康 UP 候选为空时可用；原始网络失败仍按失败阈值判定 DOWN。

超过三个探测周期加一次超时未取得确定结果时标记 STALE。STALE 与 DOWN 区分展示。探测执行器失效时，保留最近健康快照最多 60 秒；之后按全故障策略处理。重启后持久配置恢复，所有节点从 UNKNOWN 开始，禁止使用磁盘中的旧健康状态直接发布。

全故障默认采用短期 SERVFAIL，以表达已配置服务暂时失效；SERVFAIL 的缓存行为由递归解析器决定，面板不宣称其恢复时限。可显式选择“有限期使用最近健康结果”，时限默认 60 秒，且始终排除手动禁用节点；到期仍使用 SERVFAIL。没有“自动返回全部故障节点”的隐含兜底。

## 7. DNS 调度规则

先排除禁用、未知、故障和恢复观察节点，再优先选 UP，UP 为空时允许 DEGRADED。数据过期仅按上一节有限期策略处理。

- WEIGHTED：从正权重候选中随机选一个 IP，权重只描述权威 A 查询的概率。
- FAILOVER：选择优先级数字最小的候选，同优先级按权重抽样；同优先级全零权重时按稳定节点 ID 选一个。
- LOWEST_RTT：选 EWMA 请求耗时最小的候选；现选节点仍健康时，只有新候选至少快 20% 且快 20ms 才切换，最短保持 30 秒。现选节点故障时立即重新选；相同指标按稳定节点 ID 排序。
- SMART_PEAK：Asia/Shanghai 非高峰优先 NORMAL，高峰优先 PREMIUM；首选类别无可用正权重节点时回退到另一类别，然后按权重抽样。

峰值窗口采用左闭右开区间，支持跨午夜；开始与结束相同的窗口配置被拒绝。系统时钟用于业务时段，单调时钟用于超时和保持期。

每次 A 查询只返回一个入口 IP。并发探测通过原子替换不可变快照发布，DNS 请求不等待网络探测、SQLite 或辅助进程。

DNS 分配计数只统计实际生成的成功服务 A 响应。另计全部查询、各类型、错误和拒绝数量。不展示由 DNS 推算出的“实际字节流量”。

## 8. 权威 DNS 行为

只服务配置区域，不递归、不转发，RA=0。正确设置 AA，保持查询 ID；保留请求的 RD 位但不实施递归。第一版仅处理 IN 类的单问题报文；不支持的 opcode 返回 NOTIMP，非法问题数/报文返回 FORMERR，区域外和非 IN 请求返回 REFUSED。

区域 apex 返回 SOA / NS；配置的 NS 名称在区域内时提供其静态地址记录。服务名称返回选中的 A。已有名称没有对应类型时返回 NOERROR / NODATA 并附 SOA；不存在名称返回 NXDOMAIN 并附 SOA。没有 IPv6 线路时，服务名称 AAAA 返回 NODATA。区域 apex 与配置名称的空非终端名称也正确视为存在，避免错误 NXDOMAIN。

负缓存 TTL 默认 30 秒，可配置。服务名候选为空时按全故障策略返回 SERVFAIL，而非把已存在服务误报为 NXDOMAIN。

实现 UDP 和 TCP；TCP 使用两字节长度前缀、精确读取、空闲超时和每连接请求数限制。限制报文大小、连接数和并发请求。UDP 默认 512 字节，兼容 EDNS0 的合理缓冲区并上限 1232；超长响应设置 TC，允许 TCP 重试。畸形输入只影响当前请求。

公网 DNS 和 Web 管理端口分离。权威响应固定小规模且不支持 ANY 放大响应；安装文档包含基础速率限制建议，但不会未经配置改写整机防火墙。

部署文档提供真实父区 NS 委派示例、区域内 NS 的 glue 条件、至少两个独立权威节点的生产建议和 `dig +trace` 验证。第一版单节点部署明确标注共置单点；备用 NS 地址不会虚构为独立可用节点。

## 9. Web API 与面板

顶部展示 DNS/API/探测执行器状态、候选池、模式、时区与高峰状态、查询计数、配置版本。节点表展示维护开关、健康级别、入口 IP/端口、类别、权重、优先级、最近请求耗时、最近 20 个确定样本的成功率、观测时间、出口验证状态、DNS 分配次数与占比。

支持节点新增、编辑、删除、单节点导入、手动探测、全局配置编辑、模式切换、最近 50 条事件。配置输入采用显式保存和服务端校验；权重操作防抖并显示保存状态。节点凭证默认遮罩，列表和日志不返回完整 UUID/密钥，编辑允许保留原值。

初次启动生成随机管理令牌，文件权限 0600，管理 API 使用 Authorization Bearer 鉴权和恒定时间比较；令牌不放入 URL，浏览器默认只在当前标签页内存保存。静态登录页可匿名访问，所有状态、配置和操作 API 均需鉴权。API 不开放跨域，前端输出按文本渲染。明确 HTTP 本机访问和 HTTPS 公网访问的部署区别。

事件记录状态变化、配置变化、进程重启和关键错误，包含节点 ID、时间和配置版本；环形内存最近记录配合有上限的 SQLite 事件保留，避免无界内存和日志增长。

## 10. 安装、启动和故障处理

install.sh 面向 Ubuntu/Debian，以专用系统用户、虚拟环境和 systemd 部署。程序安装到 /opt/smart-dns-lb，配置/数据库位于 /var/lib/smart-dns-lb。监听低端口使用 systemd CAP_NET_BIND_SERVICE，服务进程不以 root 运行。

安装前检测 UDP/TCP 53 占用、Python 版本、架构和依赖，检查完成后再变更系统。脚本不自动关闭 systemd-resolved；冲突时列出占用进程及选择指定地址监听、调整现有服务的步骤。默认不改写 /etc/resolv.conf，不修改现有 3x-ui 服务。

Mihomo 支持传入本地可执行文件路径；下载为显式选项，固定发行版本和架构、核对发布校验值，并记录版本。安装控制服务可以先完成；真实探测在二进制和节点配置就绪前明确显示未配置。

生成 systemd 服务、示例环境配置、管理令牌和启动状态检查。DNS 绑定失败导致进程非零退出，不允许 Web 页面把未启动的 DNS 展示成正常。普通网络超时、异常 DNS 报文及单节点错误只记录为局部事件。

退出时关闭 DNS 监听、取消探测、终止受管理子进程并关闭数据库。配置写入事务失败时保留原配置和原生效版本；API 返回明确错误。

## 11. 验收与测试

1. 协议级 DNS 测试覆盖 UDP/TCP、A、AAAA、SOA、NS、NXDOMAIN、NODATA、区域外查询、EDNS、畸形请求、截断及全故障响应。
2. 状态机使用可控时钟验证失败阈值、恢复观察、延迟防抖、观测过期、全故障时限、重启和维护优先级。
3. 调度测试覆盖权重零值、主备、最低延迟滞回、跨午夜时段、NORMAL/PREMIUM 双向回退。加权测试验证概率区间，而非逐次严格配额。
4. 探测测试模拟入口 accept 成功但后端不可达、认证失败、出口不符、目标故障、辅助进程崩溃、节点修改期间旧结果返回；保证这些情形不会被 TCP 成功掩盖。
5. API 测试覆盖鉴权、非法配置、秘密字段遮罩、保存失败、并发编辑版本冲突和禁用状态重启保留。
6. 实际 Mihomo 集成测试验证每个本地 SOCKS 入口固定路由、TLS + TCP / WS / gRPC 配置、正确证书校验及出口标识。需要真实服务器的项目明确标注为部署后验收，不伪造通过结果。
7. 本地以非特权端口启动应用，验证面板状态、DNS 真实查询、持久化、关闭和重启。安装脚本做语法检查；Linux systemd 和真实 NS 委派在对应环境执行并记录结果。
8. 最终现场分别阻断三条转发路径、停止落地 VLESS 服务、恢复节点，记录故障发现时间、权威答案变化时间和实际 Mihomo 客户端恢复时间。

## 12. 实施顺序与完成条件

按配置/状态模型、DNS/调度、真实探测/API、面板、安装文档、集成验证的顺序交付。全部在当前项目中完成，不直接登录或改动用户服务器。

代码交付完成条件是：本地可运行、有适配部署的安装脚本和文档、自动检查结果可核对、真实环境尚待执行的验证项目清晰列出。用户应先审阅本设计，确认 Python 主程序加 Mihomo 辅助进程这一架构调整，再进入实现。
